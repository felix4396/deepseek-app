# 协作流程：Issue 驱动开发

本仓库以 GitHub Issue 作为唯一任务源。聊天、临时文档都不算任务状态。

## 1. 认领任务

1. 在 Issue 下评论 `/claim`，并说明你的分支名。
2. 维护者把 Issue 指派给你，状态标为 `status:in-progress`。
3. 认领后 48 小时内没有 commit 或说明，任务回收到 `status:todo`。

## 2. 分支与提交

分支命名：

| 用途 | 命名 |
| --- | --- |
| 功能 | `feat/<短名>` |
| 修复 | `fix/<短名>` |
| 测试/验证 | `test/<短名>` |
| 发布准备 | `release/<版本>` |

基线规则：

- 修 bug 从最近一次发布 tag 拉分支，避免混入未验收改动。
- 集成验证从 `integration/next` 拉分支。
- 禁止直接向 `main` 推送；发布由维护者执行。

提交信息：

```
<type>(<scope>): <一句话>

- 复现：<怎么复现>
- 修复：<改了什么>
- 验证：<命令与结果>
```

## 3. 状态标签

| 标签 | 含义 |
| --- | --- |
| `status:todo` | 已确认，排队中 |
| `status:in-progress` | 有人在做 |
| `status:blocked` | 缺外部条件，Issue 内必须写恢复动作 |
| `status:review` | 实现完成，等待验收 |
| `status:done` | 验收通过 |
| `status:paused` | 主动暂停，保留恢复动作 |

一次只能有一个状态标签。

## 4. 验收契约（缺一项不算完成）

- commit（含 changed paths）
- 复现证据：修复前的失败输出或截图
- 回归命令与真实输出（不许只写"测试通过"）
- 手机视口截图（UI 改动）：390 与 360
- 未测边界：明确写出没测什么
- 隐私检查：无 API Key、无完整 URL 凭据、无聊天/支付正文

## 5. 禁止事项

- 不提交真实 API Key、管理 Token、签名下载链接
- 不上传用户反馈原始日志与联系方式到 Issue
- 不伪造测试通过、不把模拟结果写成真机通过
- 不同时启动多台模拟器；重型构建串行
- 不 `git add -A` 提交无关改动

## 6. 发布

发布由维护者按门禁执行：

1. 同变体、更高 `versionCode`
2. SHA-256 与证书指纹校验
3. manifest 与 APK 双向核对
4. 双端下载字节一致
