## #30（P0）反馈弹窗在真机 WebView 上无法滚动

### 可验证的断言

> 「在 Android WebView（API31/Chrome91/beta.7、API33/Chrome109/beta.8）上打开设置 → 数据管理 → 写反馈，弹窗内容超出一屏，手指上滑内容不动；日志显示触摸事件全部到达（start 13 / move 163 / end 13），但 `scrollTop` 恒为 0，内容 1974px、可视 491px。」

### 复现方法与环境

脚本 `_scratch/repro.mjs` 的 `issue30()`，同一 360×640 触摸上下文跑三种工况：

| 工况 | 构造方式 | 目的 |
| --- | --- | --- |
| `baseline` | 原样 HEAD 构建 | 桌面 Chromium 是否复现 |
| `no-bounded-height` | 把 `.feedbackDialog` 的 `max-height/height` 与 `.feedbackMain` 的 `max-height/flex` 去掉（**模拟真机上「高度约束链没生成有界盒子」**） | 复现真机症状 + 验证 `preventPageScroll` 的失败模式 |
| `no-dvh` | 遍历所有样式表，删掉所有含 `dvh` 的声明（**模拟不支持 `dvh` 的 WebView**） | 排除「dvh 是根因」（对照 #13） |

步骤：注入 `localStorage['chat-demo:api-key']` → `?diag-debug` → 写 30 条诊断日志 → 边栏 → 设置 → 数据管理 → 写反馈 → 打桩 `Event.prototype.preventDefault` 计数（只统计 `type==='touchmove'`）+ capture 阶段 `touchmove` 计数 → CDP 连划 16 次（每次 touchStart + 12 touchMove/16ms + touchEnd）。

### 结论

| 维度 | 结论 |
| --- | --- |
| 桌面 Chromium 360×640 真触摸 | **通过**（scrollTop 0→356，`preventDefault`=0）→ **#30 在桌面 Chromium 上不复现** |
| 真机 WebView（API31/API33，用户日志） | **确实失败**（`scrollTop` 恒 0、事件全到） |
| 「dvh 缺失导致滚不动」这一假设 | **不成立**（`no-dvh` 仍滚 356） |
| 失败介质 | **仅在真机 WebView 复现**；但**失败机制在桌面 Chromium 可复现**（`no-bounded-height` 工况 176/176 被取消） |

**「CDP 触摸事件到达但什么都不滚」的机制（已由代码 + 上面第 2 工况实证）：**

1. `src/app/viewport.ts:35-43` 在 `document` 上以 `{ passive: false }` 注册 `touchmove → preventPageScroll`。
2. `src/app/viewport.ts:13-32` 的 `preventPageScroll` 只在**单指**时生效，从 `event.target` 沿祖先链走到 `document.body`，逐个读 `getComputedStyle`：
   - `scrollsY = /auto|scroll/.test(overflowY) && el.scrollHeight > el.clientHeight`
   - `scrollsX = /auto|scroll/.test(overflowX) && el.scrollWidth > el.clientWidth`
   - 命中任一 → `return`（放行）；
   - **一个都没命中 → `event.preventDefault()`（`viewport.ts:31`）**。
3. 所以只要 `.feedbackMain` 因为丢掉了高度约束而 **`scrollHeight === clientHeight`（不溢出）**，扫描就认为「这一片没人能滚」，于是把**每一次** `touchmove` 的默认行为取消。触摸事件照常派发给 JS（176 条全到，与用户日志 start13/move163/end13 同型），但浏览器的滚动动作被拦死；同时 `html, body, #root` 在移动端本来就 `overflow:hidden` + `overscroll-behavior-y:none`（`src/app/global.css:46-53`），页面级滚动也没有退路 → **弹窗内容彻底不可达，且全程零报错**。

于是「滚不动」不是滚动容器写错了属性，而是 **两层叠加**：
- **布局层（为什么没有可滚动的盒子）**：`.feedbackMain` 能滚，前提是父链把高度夹死：`src/components/settings/Settings.module.css:781-796` `.feedbackDialog{max-height:calc(var(--modal-viewport-height,100vh) - 32px)}` → `:799-811` `.feedbackMain{flex:1 1 auto;min-height:0;max-height:560px;overflow-y:auto}`。而 `--modal-viewport-height` 由 `src/components/base/Modal.tsx:47-68` 在 `useLayoutEffect` 里写入，**且 `visualViewport.scale !== 1` 时直接跳过**；`Modal` 是挂到 `body` 的 portal，不在承载键盘视口变量的 app frame 内。
- **交互层（为什么不滚也不报错）**：`src/app/viewport.ts:31` 的失败方向是**失败即全锁（fail-closed）**，任何「布局层意外没生成有界盒子」的偏差都会被它放大成整块内容不可达，而不只是「少滚一点」。

### 根因（file:line）

1. `src/app/viewport.ts:13-32`（尤其 `:31` `event.preventDefault()`）+ `src/app/viewport.ts:35-43`（注册点）—— 全局 `touchmove` 拦截在「找不到可滚动祖先」时反向锁死整页，且不区分「这块区域本来就不该滚」与「这块区域本该滚但布局没兜住」。
2. `src/components/settings/Settings.module.css:781-796` / `:799-811` —— 滚动容器的有界性依赖一条跨模块的约束链（父弹窗 `max-height` ← JS 写的 CSS 变量 ← `visualViewport`），任一环失效即退化为「不溢出 → 不可滚」。
3. `src/components/base/Modal.tsx:47-68` —— 变量写入条件过窄（`scale !== 1` 跳过），且是不在 app frame 内的 body portal，键盘/缩放场景下拿不到 `useMobileViewport` 的修正值。

### 修复方案（#30，P0，优先级 1）

**改动 A（根治 fail-closed，必做且最小）**：删掉 `document` 上的 `touchmove` 拦截，改由 CSS 承担同样的职责。

- 依据：移动端 `html, body, #root` 已是 `height:100%; overflow:hidden; overscroll-behavior-y:none`（`src/app/global.css:46-53`），app frame 是 `position:fixed`（`src/app/App.module.css:97-107`），**页面本身在设计上就不可能滚**——JS 锁是冗余的；而它的失败模式（布局一有偏差就整块锁死）才是 #30 的真凶。
- 具体改：`src/app/viewport.ts` 删除 `preventPageScroll` 与 `usePreventPageScroll` 的调用点；保留 `useMobileViewport`。若需保留「不让页面橡皮筋」，加到 `global.css` 的 `html{ overscroll-behavior-y: none }`（已有 `body`、`#root`，补 `html` 级）。
- 影响面：所有触摸滚动路径（消息列表、侧边栏、设置各分组、反馈弹窗）。这是**正向**扩散——原来「本该能滚但因祖先扫描漏判而被拦」的容器全部恢复；风险是「本不该滚的区域开始能滚」，由 `overflow:hidden` + `overscroll-behavior` 兜住。

**改动 B（布局层兜底，必做）**：让 `.feedbackMain` 不依赖 JS 变量也能滚。
- `Settings.module.css:781-796`：`.feedbackDialog` 保持 `max-height: calc(var(--modal-viewport-height, 100vh) - 32px)` + `@supports (max-height:100dvh)` 覆盖（**不要**双声明，见该处 #13 注释）。
- `.feedbackMain:799-811` 增加一个**自身可控**的兜底上界，例如 `max-height: min(560px, calc(100vh - 200px))`，并在 `@supports (max-height:100dvh)` 内提供 `100dvh` 版本；保持 `min-height:0; flex:1 1 auto; overflow-y:auto; touch-action:pan-y; overscroll-behavior-y:contain`。
- `Modal.tsx:47-68` 去掉 `visualViewport.scale !== 1` 的早退，改为「`scale !== 1` 时用 `window.innerHeight`」而不是不写；这样键盘/缩放两种情况下变量都有值。

**改动 C（按 issue 要求补埋点，必做）**：在 `FeedbackDialog` 打开时与键盘 `resize` 时各记一条诊断日志：`visualViewport.height` / `scale` / `--modal-viewport-height` / `dialog.getBoundingClientRect()` / `feedbackMain.scrollHeight|clientHeight|scrollTop|overflowY`。这是把「不可判定」变成可判定的唯一手段（issue 的 next action 本身也要求先加埋点）。

- **回归命令**：
  - 构建：`DIST_OUT=dist-scroll NODE_ENV=production npx rspack build -c rspack.config.ts`
  - 真触摸回归：`node tests/run-layer.mjs integration --only feedback-scroll --timeout-ms 600000`（真实约 191~200s，`dist-scroll/` ≠ `dist/`，见 `tests/README.md:116,157`）
  - 三工况本地复现：`node _scratch/repro.mjs 30`，期望 `baseline.scrolled=true`、`no-dvh.scrolled=true`、**`no-bounded-height.scrolled` 也从 `false` 变 `true`**（改动 A 生效后，即使布局退化也不该整块锁死）
  - 全量：`pnpm test` + `pnpm run type` + `pnpm run lint`
- **未测边界**：真机 ColorOS 13.1 / Reno6 + 真实 IME、真实系统字体缩放、Chrome 83 及更老内核、iOS WKWebView、393×851 + 键盘同屏；`--modal-viewport-height` 在真机 `visualViewport` 上的实际取值（本机无法采集，必须靠改动 C 的埋点）。**本次未在真机上验证过任何修复**。
- **UI 截图**：改动 A/B 触及弹窗布局，按仓库标准必须补 **390 / 360 两套截图**（改动前后各一组，含键盘弹出态）。

## #28（P1）设置里填完 API Key 退出设置 → 白屏

### 可验证的断言

> 「在设置里输入 API Key、退出设置，界面变成整片白屏，什么都点不了，只能杀进程重进。」

### 复现方法与环境

脚本 `issue28()` 两段：

- **S1（issue 描述的那条路径）**：390×844 → 清 `localStorage` → 重载 → 应用自动弹设置（或手动开）→ `input[type=password]` 填 `sk-g5-local-fixture` → 点「确定」→ 记录 `#root` 子节点数 / `body.innerText` 长度 → 点「关闭」退出设置 → 700ms 后复查。
- **S2（白屏的后果链）**：注入 key → 打桩 `/v1/chat/completions` 返 500、`/v1/models` 返 200 → 真的发一条消息（落到 IndexedDB `chat-demo` 的 `sessions`，`msgCount=2`）→ 打开 IndexedDB 把 `messages[0].files = null`（原值 `[]`）→ 重载 → 从边栏点进该会话 → 记录 `#root` 子节点数 / `innerText` 长度 / `pageerror`。

### 真实证据（`_scratch/evidence/repro.json`）

```
# S1 填 Key → 确定 → 关闭设置
hasPw = 1
before: rootChildren=1 textLen=370
after : dialogs=0 rootChildren=1 textLen=47  stored="present"   errors=[]
whiteScreen = false            ← 没有白屏

# S2 files=null → 重载 → 点进会话
sessions.sessionCount = 1, patched = ["1038dddc-…"], firstFiles 原值 "[]" → null
rendered: rootChildren=0  textLen=0  domNodes=14  root.innerHTML=""
errors: ["TypeError: Cannot read properties of null (reading 'length')"]
whiteScreen = true             ← 白屏复现（真实、桌面 Chromium）
```

### 结论

| 维度 | 结论 |
| --- | --- |
| 「填 API Key → 退出设置」这条**具体路径** | **通过**（桌面 Chromium 无白屏；与 issue 评论里 16 个 Playwright 场景全绿一致）→ **桌面不复现** |
| 「一次渲染抛错 → 整个 App 白屏」这个**后果与机制** | **确实失败**，在桌面 Chromium 用脏持久化数据稳定复现（`TypeError` → `#root` 子节点 0、DOM 仅剩 14 个节点、`innerText` 长度 0） |
| 真机上到底哪一步抛的错 | **不可判定**（需要 issue 里那条「20MB 导入 / 2962ms 长任务 / 嵌套确认框 z-index」组合下的真机日志；本机只能证明「有错即白屏」） |

即：#28 的**触发器**是环境/数据相关的（真机、特定数据、内存压力），本机无法钉死；但**它之所以是白屏而不是报错/局部降级**，原因在代码里是确定的 —— 全局没有错误边界。

### 根因（file:line）

- **没有全局错误边界**：全仓 `src/` grep `ErrorBoundary` / `componentDidCatch` / `getDerivedStateFromError` **0 命中**；`src/main.tsx` 的 `createRoot` 未传 `onUncaughtError`。→ 任意一处渲染期抛错，React 18 卸载整棵树，`#root` 直接空掉。
- **渲染期不设防的读取点（已实证的一个）**：`src/components/messages/UserMessage.tsx:46` `const canSend = !busy && (draft.trim() !== '' || message.files.length > 0)`，以及同文件 `:65`（`.some`）、`:69`（`.map`）—— 持久化数据里 `files` 为 `null`（老版本数据、导入数据、半途中断的写库）时立刻 `TypeError`。同类「读持久化字段直接假设结构」的点还有 `src/components/messages/UserMessage.tsx:99` 附近等。

### 修复方案（#28）

**改动 A（必做，1 处，收益最大）**：加全局 `ErrorBoundary`。
- 新增 `src/app/ErrorBoundary.tsx`（class 组件，`getDerivedStateFromError` + `componentDidCatch` 记一条诊断日志走 `collector`），在 `src/main.tsx` 的 `<App />` 外包一层；`createRoot(el, { onUncaughtError })` 同时接住异步/事件期错误。
- 兜底 UI：一句人话 + 「重新加载」按钮 + 「导出诊断日志」入口（诊断日志是本地 IndexedDB，白屏时用户仍能自救）。
- 影响面：全局。风险是「原本会白屏的错误变成静默降级」，用 `componentDidCatch` 写诊断日志 + 兜底 UI 上带错误摘要来抵消。

**改动 B（必做，防御式归一化）**：在消息从 IndexedDB 读出的边界上做一次 normalize（`files: Array.isArray(x) ? x : []`，`content: typeof x === 'string' ? x : ''`），而不是在每个组件里判空。

## 汇总：哪些是桌面 Chromium 复现，哪些只有真机 WebView

| Issue | 桌面 Chromium（真实触摸/真实渲染） | 真机 WebView | 判定 |
| --- | --- | --- | --- |
| **#30** 反馈弹窗滚不动 | **不复现**：360×640 真触摸 `scrollTop 0→356`，`preventDefault`=0 | 复现（用户日志：move 163、`scrollTop` 恒 0） | 仅真机；但失败机制（`preventPageScroll` fail-closed）在桌面用 `no-bounded-height` 工况稳定复现（**176/176 次 touchmove 被 `preventDefault`，`scrollTop` 0→0**） |
| **#31** 取消后丢草稿 | **复现**：填→取消→重开，正文/联系方式双空，`localStorage` 无草稿键 | 无需真机 | **确实失败**（两端一致） |
| **#28** 填 Key 退出设置白屏 | 具体路径**不复现**（S1 无白屏；与 issue 评论 16 场景全绿一致） | 复现（用户反馈） | 具体触发路径**不可判定**；「一次抛错 → 整树白屏」的后果链**确实失败**（`TypeError: Cannot read properties of null (reading 'length')`，`#root`=0、DOM=14、`innerText`=0） |

**排除了一个流行误判**：`dvh` 缺失**不是** #30 的根因（`no-dvh` 工况仍 `scrollTop 0→356`）。真凶是「高度约束链一旦没生成有界盒子 → `src/app/viewport.ts:31` 把所有 `touchmove` 全部 `preventDefault` → 整块内容不可达且零报错」。

**全部测试都是本机桌面 Chromium 真跑，没有任何一项被当作真机通过。** 真机侧只引用用户提供的日志事实，未做真机验证。
