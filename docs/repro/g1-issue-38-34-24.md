### 4. 结论

- A1–A5 全部 **【确实失败】**（已复现）。
- 关键补充证据（超出 issue 原文的发现）：**预算只在「块边界」生效**。第 1 次导入的第 2 个块自适应放大到 409KB，在 64KB/s 下要 6.4s，超过 6s 预算 → 整块（在途的 409KB 字节）被丢弃，`download.bytes` 停在 4096（1%）。也就是说判死时**已经收到的字节会被整体作废**，用户看到的是「4.0KB/512KB」却已经下了 400KB。这是「stalled 判定精度」的第二个缺陷（不只是阈值错）。
- A3 的实现证据：`deadline` 在 `downloadArchive` 里一次算死，之后没有任何地方刷新它。

### 5. 根因（`file:line`）

| 位置 | 代码 | 问题 |
| --- | --- | --- |
| `src/services/chat/history/urlImport.ts:56` | `const DOWNLOAD_TOTAL_BUDGET_MS = 120_000` | 语义是「总墙钟」，且是编译期常量 |
| `urlImport.ts:631,639` | `const budgetMs = Math.max(1, options.downloadBudgetMs ?? DOWNLOAD_TOTAL_BUDGET_MS)` / `deadline: startedAt + budgetMs` | 只在开始时算一次，**进度不延长 deadline** |
| `urlImport.ts:363-417`（`withinBudget`） | `const remain = state.deadline - Date.now(); ... if (remain <= 0) recordEvent('import_stage','import: download budget exhausted'); finish(() => reject(new DownloadBudgetExceeded()))` | 判据是「remaining≤0」，与「上次收到字节距今多久」无关 |
| `urlImport.ts:530-613`（`fetchChunk`） | 每次原生请求前包一层 `withinBudget`，块返回后才累加字节 | 预算检查粒度 = 块；块越大越容易整块作废 |
| `urlImport.ts:723-724` | `chunkSize = clamp(bytes/elapsed*CHUNK_TARGET_MS, MIN, MAX)` | 自适应只按速率放大，不考虑剩余预算 |
| `urlImport.ts:746-762` | `catch(DownloadBudgetExceeded)` → `recordDownloadFailure('stalled', …, 'budget.ms', 'request.from', 'request.span', retryable:'yes')` → `historyImportUrlStalled/StalledUnknownTotal` | 唯一出口就叫 `stalled`，文案 `i18n/zh.ts:143` 写「下载长时间无响应」，与事实（一直在推进）矛盾 |
| `urlImport.ts:634` + `SettingsDialog.tsx:786-812, 847-856` | `state.downloaded: 0`；`retry()` 只做 `setStatus(null)` + `setSource({kind:'url',url})`，`importLink` 每次新建 `AbortController`、`setTrace([])`，无 `resumeFrom` | 跨导入零续传：`downloadedBytes` 只有导出没有回填入口 |

### 6. 修复方案

1. **把「总墙钟」换成「无进展看门狗」**（改 `urlImport.ts:56/333-342/363-417`）：`DownloadState` 增加 `lastProgressAt`，每收到一块字节就 `state.lastProgressAt = Date.now()`；`withinBudget` 判据改成 `now - lastProgressAt > idleMs`（默认 45s）。保留一个**硬上限** `hardCapMs = max(120_000, ceil(total / 实测速率) * 3)`（封顶 30min）防僵尸下载。
2. **块大小对预算收敛**（改 `urlImport.ts:723-724`）：`chunkSize = min(chunkSize, rate * min(CHUNK_TARGET_MS, remainIdle))`，避免「一块吃掉整个预算、在途字节整块作废」——这正是 r2 里 409KB 块那一幕。
3. **失败语义与日志分离**：区分 `reason='stalled'`（无进展，带 `idle.ms`、`last.progress.from`）与 `reason='over-budget'`（硬上限），两者都带 `download.bytes`/`download.total`/`budget.leftMs`；文案 `i18n/zh.ts:143-144` 改成「已下载 X/Y，N 秒没有新数据」或「超过最长下载时间」。
4. **重试续传**（改 `UrlImportOptions` + `SettingsDialog.retry`）：新增 `resumeFrom?: number`，`downloadArchive` 用它初始化 `state.downloaded/from`；`retry()` 把上次失败的 `downloadedBytes` 传回去。服务端不吃 Range（回应 200 或 `from>0` 却回 200）时 fail loudly 记 `reason='no-range'` 后从 0 重来，不静默。
5. **影响面**：小包快路径不变（首个 200 响应仍然一次性拿完就结束，r3 场景 B 证实 1 次请求即成功）；会被打破的是 `tests/unit/url-import-stall.test.mjs` 里 3 处**按墙钟口径**写的断言（`elapsed >= 400`、`budget.leftMs < 400`、`budget.ms === 400`），需要改写成 `idle.ms` 口径（`downloadBudgetMs` 建议留在 options 里当测试钩子，语义变 `idleMs`）。
6. **回归验证命令**：
   ```
   pnpm test                                   # unit 层，基线 18/18
   node _scratch/r1-issue38-budget.mjs          # 期望：不再 stalled，而是下完（3.2MB@16KB/s ≥120s 仍成功）
   node _scratch/r2-issue38-retry-reset.mjs     # 期望：第 2 次导入首条 Range 是 bytes=<上次 downloaded>-…
   ```
   新增用例（放 `tests/unit/`）：慢速大包在 idle 预算内**不失败**；块放大不超过剩余 idle 预算；`resumeFrom` 生效且服务端不吃 Range 时记 `no-range`。
7. **未测边界**：iOS（原生桥实现不同，未验证）；200MB 附近的交互（交给 #24/#34）；真机 0.5MB/s 真网（本次用本地限速服务，是**等价限速**不是真网）；原生层 socket 半死（收不到 FIN）时的 idle 判定。

## 二、#34 大包导入：要不要「下载落盘 + 边下边解」

### 1. 可验证主张

| # | 主张 | 可否验证 |
| --- | --- | --- |
| B1 | 21MB 包峰值 ~125MB JS 堆（≈6x），200MB 是内存安全带 | 本机**只能部分验证**（见结论） |
| B2 | 250MB 包 ≈ 1.5GB 堆 → OOM，即「提高上限 = 报错变闪退」 | 本机**不可判定**（WebView 堆上限模型不可等价模拟） |
| B3 | 内存占用随包体线性增长，无上限保护 | 可验证 |

### 2. 复现步骤与原始证据（`_scratch/r4-issue34-memory.mjs`）

```
env -u http_proxy -u https_proxy -u HTTP_PROXY -u HTTPS_PROXY node --expose-gc _scratch/r4-issue34-memory.mjs 21|64|120|200
```

```
===== 21MB 包（22020096 字节）=====
结果 = 成功，耗时 180ms，请求 8 次    File 字节 = 22020096
基线 heapUsed = 10.0MB / rss = 82.9MB
峰值 heapUsed = 12.7MB → 放大 0.6x 包体
峰值 rss      = 117.8MB → 放大 5.6x 包体
峰值 arrayBuffers = （随包体 2.0x 量级）

===== 64MB =====  峰值 heapUsed 12.7MB / 峰值 rss 233.6MB（3.6x）
===== 120MB ===== 峰值 heapUsed 12.7MB / 峰值 rss 321.9MB（2.7x）/ 峰值 arrayBuffers 236.4MB（2.0x）
===== 200MB ===== 峰值 heapUsed 14.5MB / 峰值 rss 484.2MB（2.4x）/ 峰值 arrayBuffers 396.5MB（2.0x）
```

同进程用 `--max-old-space-size=150` 跑 200MB 包：**没有崩**（`heapUsed` 峰值 14.5MB，包体字节都在 `arrayBuffers`/external，不进 old space）。

### 3. 结论

**【不可判定】** —— 分两半说清楚：

- 可验证的一半（**通过/复现出方向性事实**）：整包字节必须**全量同时驻留**——`chunks[]` 累积（1x 包体）+ `concatChunks` 再拷一份（+1x）→ `arrayBuffers` 峰值稳定在 **2.0x 包体**，RSS 增量 ≈ **+1.1x 包体**，**没有任何与包体相关的上限**（200MB 包在这台机器上 RSS 484MB）。B3 成立。
- 不可判定的一半：issue 里「21MB→125MB（6x）」「250MB→1.5GB OOM」是 **WebView/Android 侧的数据**。本机 Node 的 `heapUsed` 不含 ArrayBuffer，`--max-old-space-size` 也管不到它，所以「6x 放大」和「OOM 闪退」在本环境**无法等价复现**，我不把它写成「已复现」。方向（随包体线性、无上限、低端机必崩）成立，倍数待真机验证。
- 顺带一个真实缺陷证据：`urlImport.ts:238` 的 `toBytes()` 用 `Math.floor(data.length*3/4) > MAX_ARCHIVE_BYTES` 估算块大小，而单块上限是 4MB（`MAX_CHUNK_BYTES`），这个判断**永远不会命中**（死代码）——200MB 实际只由 `:683`/`:690` 两处命中。

### 4. 根因（`file:line`）

| 位置 | 代码 | 问题 |
| --- | --- | --- |
| `urlImport.ts:456-466`（`requestRange`） | `CapacitorHttp.get({responseType:'arraybuffer', headers:{Range:...}})` | 数据只能经原生桥回 JS（base64），**没有落盘通道** |
| `urlImport.ts:510-521`（`concatChunks`）+ `:727-745` | 收齐后 `new File([new Blob(chunks)], …)` | 全量常驻：原文 + concat 拷一份，交给解析层再拷 |
| `urlImport.ts:19` | `MAX_ARCHIVE_BYTES = 200MB` | 唯一的内存保护就是这一条硬阈值（不是分层配额） |
| `urlImport.ts:238` | `toBytes()` 的块级估算 | 死代码（4MB 块不可能超 200MB） |

### 5. 修复方案

1. **短期（不依赖新原生能力）**：用 #38 的 idle 看门狗 + 续传 + #24 的可解释超限，把「21MB 能导、164MB 慢网能续、>200MB 说明白」做扎实；`urlImport.ts:238` 的死代码删掉。
2. **架构（本单主体）**：原生侧新增 `downloadToFile(url, {resumeFrom, onProgress})`（`@capacitor/filesystem` 或自定义流式插件）→ 直接写 `Directory.Cache` 临时文件，**不过 base64 桥、不进 JS 堆**；JS 侧用现成 `zipReader.ts`（328 行）改成增量/分片读取解压。落盘后 `MAX_ARCHIVE_BYTES` 改由「磁盘余量/配额」决定（例如 1GB），内存路径（Web / 老客户端）保留 200MB 并给出对应文案。
3. **临时文件生命周期**：成功 → 解析完成后删；失败/取消 → `finally` 删；启动时清理 24h 以上残留。三者都要有断言（见下方回归）。
4. **影响面**：`DownloadState` 状态机与进度语义（stage/downloaded/total/cancellable/heartbeat）要**继承**而不是重写，否则 #38 的日志与文案全失效；`toLocal.ts`/`importArchive.ts` 的入参由 `File` 改成「文件路径 + 读取器」需要一层适配（`importHistory(file, …)` 签名会变）。
5. **回归验证**：
   ```
   pnpm test && pnpm test:integration
   # 真机（PJB110 / Android 14）：
   #  21MB / 329 会话包 → 会话数、图片数与改前一致
   #  >200MB 包 → 导入成功，峰值 RSS 不随包体线性（devtools memory 采样）
   #  失败/取消后 Directory.Cache 无残留
   ```
6. **未测边界**：iOS；低存储设备（磁盘不足时的表现）；Web 端（无 Filesystem）；`zipReader.ts` 是否真的能流式（需先确认，否则要先改解压层）。

C 场景的服务端视角：`[{"range":"bytes=0-4095","status":206,"sent":4096,"content-range":"bytes 0-4095/262144000"}]` —— **1 次请求、3ms、0 字节提交**，与 issue 里那张证据表逐项吻合。

### 4. 结论

- **C1 →【确实失败】**：`historyImportUrlTooLarge` 的触发点只有两处（`:683` 头部声明总长、`:690` 实际下载量），C 场景命中的是 `:683`，声明的数字来自服务器自己的 `Content-Range`。判定依据正确，结论正确——**是真实超限，不是把 21MB 算成 200MB**。
- **C2 →【通过（未复现出问题）】**：8 种头部形态（含同名多值 join、缺 Content-Range、通配 `*`、全大写带空格、`Content-Length: 0`）**没有一种**能把合法包顶到 >200MB。`Number(raw)` + `isSafeInteger` 的写法（`:158-165`）对 `"21195845, 21195845"` 给 `NaN` → 视为未知，不误判。
- **C3 →【确实失败】**：`tooLarge()` 抛错前**没有 `record()`**，`import_error` 记录数 0；`SettingsDialog.tsx:810` 的 catch 只 `setStatus`。对比 H 场景（`historyImportUrlBadResponse` 有 1 条完整 `import_error`，含 `reason:'empty'`）——同一文件里两种失败，一种有证一种无证。
- **C4 →【确实失败】**：`206` 缺 `Content-Range` 时 `state.total` 从 `contentLength()` 取到**块长 4096**，于是进度条把 4096 当整包总量（`bytes 0-4095/*` 同样落到 4096），用户看到的是「已下载 21MB / 总量 4096」这种自相矛盾的进度，且 `historyImportUrlInterrupted`（`:731`）永远判不出「少下了」。

### 5. 根因（`file:line`）

| 位置 | 代码 | 问题 |
| --- | --- | --- |
| `urlImport.ts:178` | `const tooLarge = (): never => fail('historyImportUrlTooLarge', { size: maxMegabytes })` | 失败前**零日志、零上下文**（无 contentLength/contentRange/total/downloaded/maxBytes/脱敏 URL） |
| `urlImport.ts:683` | `if (state.total !== undefined && state.total > MAX_ARCHIVE_BYTES) tooLarge()` | 触发点 1（头部声明），无 phase 标记 |
| `urlImport.ts:690` | `if (state.downloaded > MAX_ARCHIVE_BYTES) tooLarge()` | 触发点 2（实际下载），同无标记 |
| `urlImport.ts:681-686` | `state.total = contentRangeTotal(headers) ?? contentLength(headers)` | 206 且无 `Content-Range` 时回落到**块长** → 伪造总量（C4） |
| `urlImport.ts:146-176` | `headerValue()`/`contentLength()`/`contentRangeTotal()` | 只取单值、无来源标记，无「谁说的这个数」的记录 |
| `SettingsDialog.tsx:710-717, 810` | `urlErrorStatus()` → `{key, params}` + `setStatus` | 兜底文案只有「文件过大（200MB），暂不支持」，无 `declared` |

### 6. 修复方案

1. **给超限分支补证**（`:178`）：`tooLarge(ctx: {source:'header'|'downloaded', contentLength?, contentRange?, total?, downloaded, maxBytes, phase})`，抛错前 `record('import_error','error','import: archive too large', {reason:'too-large', ...ctx, 'url.host': schemeHost(url)})`（URL 只留 scheme+host+路径类别，脱敏）。
2. **判定来源单一化**：把 `:683`/`:690` 合成 `assertWithinLimit(state, phase)`，日志里带 `phase:'header'|'stream'`，让「服务器说 250MB」和「真下超了」可区分。
3. **文案可解释**：`historyImportUrlTooLarge` 加 `{declared}` 参数，zh/en 两处改成「服务器声明 {declared}MB，超过 {size}MB 上限，暂不支持」。
4. **修 C4**：`state.total` 只在「有 `Content-Range` 总长」或「`status===200` 整包」时采用 `contentLength`；`206` 且无总长时保持 `undefined`（未知），进度显示「已下载 X / 总量未知」，`downloaded === 0 || downloaded < total` 的判定已兼容 undefined（`:727-745`）。
5. **顺带清掉 `:238` 死代码**（见 #34 节）。
6. **影响面**：`state.total` 语义修正会影响「进度百分比上限」显示（未知总量时只能显示已下载量）；`tests/unit/url-import-stall.test.mjs` 对 `download.total` 的断言用的是带 `Content-Range` 的 206，不受影响；i18n 两处文案 + 新增 params 需要同步。
7. **回归验证**：把 `_scratch/r3-issue24-toolarge.mjs` 的 8 场景矩阵搬成 `tests/unit/url-import-too-large.test.mjs`，断言：C 有 1 条 `import_error` 且字段齐全（reason/observed.*/maxBytes）；D/F 的 `total` 为 `undefined` 而不是 4096；A/B/E/G 正常导入 21,195,845 字节；H 仍报 `BadResponse`。命令：`pnpm test`。
8. **未测边界**：真实 OBS/CDN 的响应头（本次是本地伪造 HTTP，非真实桶）；`Content-Length` 与实际字节不符的恶意/异常服务端；iOS（`CapacitorHttp` 响应头形态需另测）；重定向（3xx）后的头部。

## 四、三条是否同源

**不是同一个 bug，但共享同一层缺失的抽象。** 三条都不该合并（各自关闭条件与验证路径不同），但**代码病灶重叠度很高**，可以用一个 PR 共用三个部件。

| 维度 | #38 | #24 | #34 |
| --- | --- | --- | --- |
| 判定对象 | **时间**（预算） | **体积**（上限判定来源） | **体积**（承载方式） |
| 触发条件 | 合法包（<200MB）+ 慢网，总耗时 >120s | 服务器声明总量 >200MB（首块头部即可判） | 包体接近/超过 200MB（内存路径无上限） |
| 现在的表现 | `stalled` 误判 + 已下字节作废 + 重试归零 | 报 `文件过大（200MB）` 且零日志、无 `declared` | 只能靠 200MB 硬阈值挡，抬高即闪退风险 |
| 共享病灶 1 | `urlImport.ts:56` / `:19` 都是「一次性硬阈值常量」 | 同左 | 同左 |
| 共享病灶 2 | `DownloadState`（`:333-342`）只有 `startedAt/downloaded/total/deadline` | 缺「这个 total 是谁声明的」字段 | 缺「数据存在哪」（内存/文件）字段 |
| 共享病灶 3 | 失败出口 `:746-762` 有日志 | 失败出口 `:178` **无**日志 | 失败出口未区分「内存路径/落盘路径」 |
| 修复部件 | `lastProgressAt` + 块大小对剩余预算收敛 + `resumeFrom` | `assertWithinLimit(phase)` + 脱敏观测字段 + total 推导修正 | 原生落盘通道 + 增量解压 + 临时文件生命周期 |

结论句子：

1. **#38 与 #24 同源度最高**：两者都在 `downloadArchive` 的同一个 `DownloadState` + 同一个失败出口上，一个缺「上次有进展的时刻」，一个缺「声明的来源」，改一个 `DownloadState` 就能同时容纳两者的观测字段。
2. **#34 与 #24 同源**：`MAX_ARCHIVE_BYTES` 是同一条阈值，判断「超没超」和「超了能不能扛」用的都是它；#24 修判定与解释，#34 换承载方式，顺序上应先 #24（判定可信）再 #34（放开上限）。
3. **#38 与 #34 有语义冲突，必须显式裁定**：#34 关闭条件写「保留 120s 总预算」，而 #38 要求改成「无进展超时」。按 #38 的口径改后，#34 那句话要改成「保留无进展看门狗 + 硬上限」，否则两条 issue 互相打回。
4. **优先级**：先 #38（合法包 100% 必失败，P0 且改动只在 JS 侧）→ 再 #24（补日志与文案，改动小、可立刻让下一份用户反馈可判）→ 最后 #34（需要原生能力 + APK + 真机，周期最长）。
