## #37 非官方渠道上传附件 404

### 可验证主张
非官方渠道（内测默认渠道 `ours`）里上传图片/文档，客户端把请求发到
`{baseUrl}{paths.messages}/files` = `http://62.106.70.167:60010/v1/chat/completions/files`，
上游回 `404 page not found`；界面上只显示「上传失败」，看不到状态码；多图会连发多条同样的 404。

### 复现（真实客户端代码 + 本地 mock 上游，未触网）
入口 `_scratch/entry37.ts` import 的是仓库真实模块（`src/services/api/client.ts`、`apiConfig.ts`），
用 `_scratch/rspack.repro37.config.mjs` 打包成 `_scratch/dist/repro37.cjs`（源码里的 `.js` 后缀 import 与
构建期常量 `__API_ORIGIN__` 只有打包器认得）。`globalThis.fetch` 被包一层：**记录原始 URL 与方法**，
只把 origin 换成 `127.0.0.1:<本机端口>` 转给本地 mock server，因此绝不会打到 `62.106.70.167`。

实测输出：

```
=== #37 环境 ===
渠道 kind = ours | protocol = openai | paths.messages = /v1/chat/completions
caps.vision = false
getMessagesBaseUrl() = http://62.106.70.167:60010/v1/chat/completions
uploadFile() 会拼出 = http://62.106.70.167:60010/v1/chat/completions/files

=== 客户端真实发出的请求 ===
POST http://62.106.70.167:60010/v1/chat/completions/files
  multipart 字段顺序: ["file:file=(screenshot.png, image/png, 111048 bytes)"]

=== mock 上游收到的原始请求 ===
POST /v1/chat/completions/files | multipart/form-data; boundary=----formdata-undici-004018150657 | Bearer …al-key（已脱敏） | 111223 bytes
  body 前缀: "------formdata-undici-004018150657\r\nContent-Disposition: form-data; name=\"file\"; filename=\"screenshot.png\"\r\nContent-Type: image/png\r\n\r\nAAAA…"

=== uploadFile() 结果 ===
rejected: ApiError kind=http status=404 message="404 page not found"
```

（响应体 `404 page not found` = 18 字节，与 issue 遥测里的 404 一致。）

同一条结果继续往下走的界面表现（静态证据）：
`describeUploadError` 只有两个具名分支（`serverBusy`、`parseFailed`），404 落到兜底的
`{ key: 'uploadFileStatusFailed' }`（「上传失败」）——见 `src/services/attachments.ts:65-75`；
`classifyStatus` 只对 401/402?/413/429/≥500 分类，404 归 `other`（`src/services/api/errors.ts:17-34`）。
即 `client.ts` 里保留下来的 `status=404` 一路没人展示。

### 根因（文件:行）
1. **路径拼错**：`src/services/api/client.ts:184-203` `uploadFile()` → `${getMessagesBaseUrl()}/files`；
   `src/services/api/apiConfig.ts:210` `getMessagesBaseUrl = baseUrl + spec.paths.messages`。
   `src/services/api/providers.ts:175`（`ours` 块，`paths.messages: '/v1/chat/completions'`）→ 拼出
   `/v1/chat/completions/files`。Files API 是 **Anthropic Messages 的前缀路由**，OpenAI 兼容上游本来就没有这个路由，
   所以这是「客户端路径写错」，不是「上游偶发故障」。
2. **spec 自相矛盾**：同一个 `ours` spec 里 `caps.vision: false`（不支持附件）与
   `paths.messages: '/v1/chat/completions'`（附件接口挂在该前缀下）并存；`providers.ts:47-48` 把 vision 定义为
   「Files API + image/document block」，两件事被绑死。
3. **门禁只在入口，三条旁路绕过**：
   - `src/components/chatInput/ChatInput.tsx:84` `acceptFiles()` 首行 `!caps.vision` 直接 return；`:260` 回形针按钮 `caps.vision ? … : null`；
   - `src/components/chatInput/ChatInput.tsx:95-100` `retryFile()` 只查 `importingHistory` + `ensureApiKey()`，**没有 vision 门禁**；
   - `src/services/chat/drafts.ts:87-98` `retryDraftAttachment()` → `:47-58` `upload()` → `uploadAttachment`，同样无门禁；
   - `src/services/chat/store.ts:833-848` `ensureServerId()` → `:845` `uploadAttachment(...)`，被 `prepareFiles()` 用于
     「导入的历史附件没有任务，发送前按本地原件补传」。`grep -rn "vision" src/services/chat src/services/*.ts` 为空，
     **发送链路完全没有 channel 能力判断**。
4. **N 条 404**：`src/services/attachments.ts:19` `MAX_CONCURRENT = 3`，`:121-160` `enqueueUpload` 最多 3 并发，
   且单项失败不短路同批其余项 → k 张图 ≈ k 次同样的 404（与 issue 的 44 次遥测吻合）。

### 方案（对应 #37 的关闭条件，逐条）
- **端点归属**：结论是「客户端路径写错 + 上游没有该路由」。不要指望上游补 `/v1/chat/completions/files`；
  即使后端补，也应该补在 `paths` 里显式声明，而不是从 `messages` 推导。
- **不再发出该路径**：在 `uploadFile()` 入口（`client.ts:184`）加 capability 断言——
  `spec.protocol !== 'anthropic' || !spec.caps.vision` 时直接抛本地
  `new ApiError('protocol', { key: 'uploadUnsupportedChannel' })`，**一次网络请求都不发**；
  `attachments.ts:168` `uploadAttachment` 里的 `record('error', …)` 照旧记 stage/bytes，便于区分「没发出去」和「发出去了 404」。
- **不支持时禁用入口并提示**：`ChatInput.tsx:84/260` 的门禁改读新能力位（见 #43 的 `files` 拆分），
  **同时**给 `retryFile`（`ChatInput.tsx:95`）、`retryDraftAttachment`（`drafts.ts:87`）、
  `prepareFiles`/`ensureServerId`（`store.ts:845`）补同一判断——否则历史/导入消息里的附件仍会触发。
- **错误含状态码**：`describeUploadError`（`attachments.ts:65-75`）增加带状态的文案，
  如 `uploadFileStatusFailedWithStatus`（「上传失败（404）」），参数取 `ApiError.status`。
- **多图不再连发**：`enqueueUpload` 队列在首个 `http` 且 `status` 为 404/405，或
  `code === 'upstream_returned_html'`（`client.ts:99-101` 已有该错误码）时，把该批标记为「渠道不支持附件」并短路剩余排队项。

### 未测边界
- 没有向真实 `62.106.70.167:60010` 发过任何请求（按红线索性拦截），因此**不能**断言上游是否另有可用文件路由；
  端点归属的最终确认仍需要一次带凭据的真实探测或后端口头确认。
- 没有验证 `deepseek` 渠道（`caps.vision: true`）在同一份代码下的成功上传路径。
- 未做真机回归、未做 390/360 截图（#37 关闭条件里的两项）。

## #35 兑换返回 503 VERIFY_UNAVAILABLE

### 可验证主张
`POST /api/redeem` 回 `503 {"code":"VERIFY_UNAVAILABLE","message":"积分服务暂时不可用，请稍后重试","request_id":"c7d95462d90d"}`，
发生在卡密校验之前（假卡也是 503 而不是 `404 CARD_NOT_FOUND`）；前端拿这个响应给出什么。

### 回放证据（真实 `api.ts` + 假 transport 回放线上原文）
`_scratch/repro-35-36-contract.mjs`：

```
=== #35 /api/redeem 503 VERIFY_UNAVAILABLE ===
  → POST http://123.207.199.196:60012/api/redeem body={"card_no":"CARD-doesnotexist-0001","api_key":"sk-local-mock","request_id":"…"}
  结果: {"kind":"error","code":"VERIFY_UNAVAILABLE","messageKey":"oursErrUnknown","cardTail":"••••0001","retryable":true}
  界面文案 = 操作失败，请稍后重试
  OURS_ERROR_KEYS 里有 VERIFY_UNAVAILABLE 吗 = false
  OURS_STATUS_KEYS 里有 503 吗 = false
  服务端自带 message 有没有被用上 = false（代码只读 code，不读 message）
```

### 结论
**需服务端/凭据**。503 的成因在服务端依赖的积分/校验服务，本地无法复现、也不该假装复现。
本地能证明的只有一件事：前端对这类「服务端暂时不可用」的降级不足。

### 根因（文件:行）
- 服务端侧（不可本地验证）：`/api/redeem` 在卡密存在性校验之前就返回 503，说明失败点在上游依赖，不是业务校验。
- 客户端侧：`src/services/ours/api.ts:107-119` `OURS_ERROR_KEYS` 里没有 `VERIFY_UNAVAILABLE`；
  `:122-129` `OURS_STATUS_KEYS` 没有 503 → 落兜底 `oursErrUnknown`「操作失败，请稍后重试」（`zh.ts:406`）。
  `redeemCard` 的最终错误分支只读 `code`/`status`，服务端给的 `message`（本来就是中文、可读）被丢弃
  （`api.ts` 兑换错误分支，`:420-428`）。
- 已有的部分是对的：`retryable: status >= 500` → `OursServicesDialog.tsx:322-327` 会显示
  「重试（沿用同一请求号）」，用户的**手动**重试有覆盖；没有自动重试/退避。

### 前端可做（有前提：不改服务端语义，只改呈现）
1. `OURS_ERROR_KEYS` 增 `VERIFY_UNAVAILABLE → 'oursErrVerifyUnavailable'`，
   文案「积分服务暂时不可用，请稍后重试」（与后端文案一致，不再出现「操作失败」这种无信息提示）。
2. `OURS_STATUS_KEYS` 增 `503 → 'oursErrServerBusy'`（顺带给其它 5xx 一个明确文案；
   注意保留 `retryable` 分支不变）。
3. 可选：把服务端 `message` 作为副文案展示，但**必须**先加白名单/长度上限——仓库已有相反取舍
   （`attachments.ts:65-75` 注释：「服务端原文多为英文且较长，不直接展示」），所以要显式设计再开。
4. 不建议在这一轮加自动重试：唯一已知的有效动作是「等后端恢复」，自动退避只会放大对已故障服务的请求。

### 未测边界
- 未使用真实卡密/真实 Key，未走通兑换成功（`synced`/`pending`/`no_downstream` 三条成功分支只有单测覆盖）。
- 未拿到服务端日志，`request_id` 之后的原因链不明；无凭据可验证服务端何时恢复。

## #36 Web 端「点了没反应 / 提示去 App 购买」

### 可验证主张
Web 版客户端用 `fetch(..., { redirect: 'manual' })` 去读 `/buy` 的 302，跨域时浏览器只给一个
`opaqueredirect`：状态码 0、`headers.get('location')` 为 `null`、body 读不出。因此拿不到收银台地址。

### 复现（真 Chromium，两个本地 server，未触网）
`_scratch/repro-36-browser.mjs`：应用源 `127.0.0.1:3252` 的 `/buy` 回
`302 Location: http://127.0.0.1:3251/pay/submit.php?pid=1&out_trade_no=T1&money=3.00&sign=abc&return_url=x`（不带 CORS 头），
收银台源 `127.0.0.1:3251`。

```
=== fetch("/buy", { redirect: "manual" }) 拿到什么 ===
{ "type": "opaqueredirect", "status": 0, "statusText": "", "ok": false,
  "locationHeader": null, "bodyLength": 0, "bodyPreview": "\"\"", "headerKeys": [] }

=== fetch("/buy", { redirect: "follow"（默认） }) ===
{ "resolved": false, "errorName": "TypeError", "errorMessage": "Failed to fetch" }

=== window.location.assign("/buy?plan=p1") 顶层导航之后 ===
{ "url": "http://127.0.0.1:3251/pay/submit.php?pid=1&out_trade_no=T1&money=3.00&sign=abc&return_url=x",
  "title": "收银台", "h1": "cashier /pay/submit.php?pid=1&…" }
是否落到收银台域名 = true
```

### 结论
**可本地复现**（纯前端 + 浏览器语义，与后端无关）。

### 根因（文件:行）
- `src/services/ours/transport.ts:55-76` `webRequest()`：`:65 redirect: 'manual'` 的 `fetch` 之后
  `:68 const location = response.headers.get('location') ?? ''` —— 跨域时恒为 `''`。
  注释（`:8-9`、`:63-66`）已承认「Web 端不靠它取收银台地址」「Location 也拿不到」，
  但契约层仍在等这个 `location`。
- `src/services/ours/api.ts` `createOrder()`（`:546-600`）：3xx 分支只认 `result.location`，
  拿不到就退回读 JSON 的 `pay_url`；`isOpenableCheckout()`（`:525`）只接受 https。
- 契约层后果（本次回放实测）：`status: 0` → `code: 'HTTP_0'` → `oursErrUnknown`
  「操作失败，请稍后重试」。**注意**：这是 HEAD 的行为；issue 里提到的「请到 App 内购买」提示来自
  `fix/issue36-web-checkout` 分支的改法，不在 `b7b5750`。
- 现状可达性：HEAD `api.ts:40` `OURS_PAYMENT_OPEN = false`，界面只有一行「支付暂未开放」+
  禁用按钮（`OursServicesDialog.tsx:273-274`），所以**当前线上 Web 端不可达此路径**；
  一旦放开建单入口，必然踩中。

### 方案（纯前端可修，不必等后端）
1. Web 端建单改成**顶层导航**，不要用 `fetch` 读 302：
   `<a href={`/buy?plan=${planId}`}>` 或 `window.location.assign(`/buy?plan=${planId}`)`。
   浏览器实测：同一 URL 顶层导航能正常落到带签名的收银台（`sign`/`out_trade_no` 都完整）。
2. 删掉 Web 侧对 `Location` 的依赖与随之而来的 `opaqueredirect` 分支/提示
   （`transport.ts:63-64` 的注释已经写明拿不到，契约层不该再假定拿得到）。
3. 原生侧**不要动**：`transport.ts:40-49` 的 `CapacitorHttp.request({ disableRedirects: true })`
   能读到 `rawHeaders.location`；回放对照实测 `createOrder` 返回
   `{"kind":"ok","payUrl":"https://pay.xiaodouap.cn/submit.php?…"}`。
4. 服务端「把收银台地址放进 JSON `pay_url`」**不算修好**：回放实测确实能解析出 `payUrl`
   （`{"kind":"ok","payUrl":"https://pay.xiaodouap.cn/submit.php?sign=abc"}`），
   但那是要求后端不再 302——会同时改动原生与其它客户端的行为；Web 端的正确解法是导航，不是把 302 变成 JSON。
   后端值得做的只有一件事：`/return?no=&order_token=` 返回 HTML 而不是 JSON（支付完的闭环体验），
   与本 bug 无因果关系。

### 未测边界
- 未在 Android WebView / iOS WKWebView 上验证 `redirect:'manual'` 行为（Chromium 语义应当一致，但未实测）。
- 未真实支付，未验证 `pay.xiaodouap.cn` 收银台在浏览器的完整成功链路与 `/return` 落地页。
- 未验证「金额与套餐不符（money=0.10 vs 标价）」这条资损风险，那是放开支付前的前置条件，不在本 issue 范围。

## #43 文件上传不应跟随 vision 开关

### 现状确认（HEAD `b7b5750`）
- 附件入口的唯一门禁就是 `caps.vision`：`ChatInput.tsx:84`（`acceptFiles` 早退）、`:260`（回形针是否渲染）；
  拖拽走同一个 `acceptFiles`（`DragMask.tsx:12-43`）。
- `caps.vision` 只有官方 `deepseek` 为 `true`（`providers.ts:118`），`openai:139`、`anthropic:162`、`ours:185` 都是 `false`。
- `ProviderCaps` 的注释把两件事绑在一起：`vision: /** 图片等附件（Files API + image/document block） */`（`providers.ts:47-48`）。
  所以「上传跟随 vision」是**设计选择**，不是实现疏漏。
- 但即使放开入口，第二道闸在协议层：`openaiAdapter.ts:10`（注释）与请求翻译只取 `type:'text'` 块拼接，
  **`image`/`document` 块直接丢弃** → `ours`（`protocol: 'openai'`）渠道「能传不能发」。
- 叠加 #37 的结论：端点也不存在（`/v1/chat/completions/files` 404）。

### 结论
**不可判定**：方案取决于 #37 的端点归属结论 + 上游是否支持文档/多模态，二者都还没落地。
现在放开入口只会把「上传失败」暴露给更多用户（与 #43 原文判断一致）。

### 方案建议（按依赖顺序，不要跳步）
1. 先落 #37 的归属结论（客户端路径写错 / 上游不支持 / 后端补端点）。
2. **若「上游不支持」**（当前证据最支持这个）：把能力拆开——新增 `caps.files`（文档上传 + 解析）与
   `caps.vision`（图片多模态）两档；`ChatInput` 门禁改读 `files`；文档走「本地文本提取 → 纯文本消息」路径
   才能真正对非官方渠道生效（`openaiAdapter` 目前没有这条路径）。
   同时按 #37 方案补齐三条旁路的 gate（`ChatInput.tsx:95`、`drafts.ts:87`、`store.ts:845`）。
3. **若「后端补端点」**：保持 vision 绑定即可，只需把上传前缀从 `messages` 推导改成 `paths.files` 显式声明，
   本 issue 可关为「不成立」。
4. 恢复动作：在 1 有结论前**不放开入口**。

### 未测边界
- 未验证任何非官方渠道对 `document`/`image` 块的上游支持（无凭据）。
- 「本地文本提取」方案在仓库里不存在，可行性未评估（依赖选型：pdf/docx/xlsx 解析库体积与低内核 WebView 兼容性）。
- 未验证拆分 `files`/`vision` 对现有 `deepseek` 渠道的回归影响。
