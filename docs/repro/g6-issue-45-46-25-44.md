## #45 长对话框的消息加载不出来，短的新建对话可以

### 1. 可验证断言

| # | 断言 | 判定 |
|---|---|---|
| A1 | 长会话的**数据加载**（IndexedDB 读取 + 反序列化）不是瓶颈 | 实测否定 |
| A2 | 长会话的**内存处理**（分支归一化 / 可见路径 / 版本索引 / view 构建）不是瓶颈 | 实测否定 |
| A3 | 长会话的**渲染**无虚拟列、无分页，首帧同步挂载全部消息 | 静态成立 |
| A4 | 长会话的**请求上下文无裁剪**，请求体随轮数线性膨胀 | 实测成立 |
| A5 | 聊天链路**全程没有超时**，首字节不来就永远 `streaming` | 静态成立 |
| A6 | 存在「转圈永不结束」的可判定状态条件 | 静态成立（状态机可枚举） |

### 2. 证据

#### 2.1 实测：数据层与内存处理都不慢（脚本 `_scratch/long-session.mjs`）

构造方式：走仓库真实写入路径 `appendBranch` 逐轮追加，保证 `parentId/selectedChildId` 与线上一致；再调用真实 `normalizeSession / getVisibleMessages / buildMessageVersions / getContextRounds / toRequestMessages`。执行方式见 §2.4。

| 消息数 | 轮数 | 可见消息 | 上下文轮次 | 请求体条数 | 请求体 KB | normalize ms | getVisible ms | 版本索引首算 ms | 复算 ms | 复用旧对象 |
|---|---|---|---|---|---|---|---|---|---|---|
| 50 | 25 | 50 | 25 | 52 | 48.5 | 0.01 | 0.06 | 0.19 | 0.04 | true |
| 500 | 250 | 500 | 250 | 502 | 483.1 | 0.01 | 0.12 | 0.20 | 0.21 | true |
| 2000 | 1000 | 2000 | 1000 | 2002 | **1932.6** | 0.00 | 0.28 | 0.59 | 0.99 | true |

结论：
- `db.loadSession` 是单次 IDB `get`（`src/services/chat/db.ts:90-91`），一次事务取整条记录，**不是逐条读、没有 N 次往返**；配合上表，1000 轮时 `normalizeSession` 0.00 ms、`getVisibleMessages` 0.28 ms、`buildMessageVersions` 0.59 ms。**"反序列化慢 / 分支索引慢"（issue 里的假设）在本地不成立**，可以排除。
- `buildMessageVersions` 复算返回同一对象（`branches.ts:56,73` 的 `unchanged ? previous : versions`）→ 不会因为流式刷新触发历史消息重渲染循环，**"React 无限重渲染"假设也排除**。

#### 2.2 实测：逐条构建 view 也不慢（脚本 `_scratch/view-cost.mjs`）

| 轮数 | 回答数 | `buildReplyView` 全量 ms | 每句均摊 ms | `describeReply` 全量 ms |
|---|---|---|---|---|
| 25 | 25 | 0.8 | 0.032 | 0.4 |
| 250 | 250 | 1.5 | 0.006 | 0.0 |
| 1000 | 1000 | 3.9 | 0.004 | 0.2 |

JS 侧"准备数据"完全不是瓶颈（此表**不含** Markdown / KaTeX / 代码高亮的真实渲染开销，见 §7 未测边界）。

#### 2.3 静态：三处与长度强相关的无上限实现

1. **渲染无虚拟化、无分页**：`src/components/messages/MessageList.tsx:149-174` 直接 `messages.map(...)` 全量渲染；`:51` 用 `getVisibleMessages(session)` 取全量；无 `IntersectionObserver`、无窗口化、无「加载更早消息」。
2. **请求上下文无裁剪**：`src/services/chat/reply.ts:324-364` 的 `toRequestMessages` 把 `getContextRounds(history)` 的**每一轮**都塞进 `messages`，全文件没有 token 预算、没有保留轮数、没有历史摘要；`store.ts:1108-1117` 直接用这个结果拼 body。上表 1000 轮 → **2002 条 / 1.93 MB**。
3. **历史附件串行补传**：`src/services/chat/store.ts:900-920`，历史轮次里没有 `serverId` 的附件（导入的图片）在 for 循环里**逐张** `await ensureServerId(...)`，全部补完才发请求；每张都是独立 `uploadFile → request → fetch`，无超时。导入数据越多，首字节等待越长。

#### 2.5 静态：「转圈永不结束」的状态条件

转圈由两个互不相关的状态驱动，都可无限持续：

- **打开会话的转圈**：`src/app/App.tsx:110-135`，条件 `!ready || (activeId !== null && !session)`，其中 `session = state.sessionCache[activeId]`（`App.tsx:40-44`）。只有 `ensureSessionLoaded` 成功写入 `sessionCache`（`store.ts:379`）或失败写入 `sessionLoadErrors`（`store.ts:384-388`）才会离开该分支。
- **发消息后的转圈**：`ReplyArea` 的 loading，由 `store.streaming[sessionId]` 驱动（`store.ts:1077` 设置，`streamReply` 的 `finally` 里删除；`App.tsx:49-51` 判活）。
- **无超时**：`src/services/api/client.ts:95-112`（`request`）与 `client.ts:269-288`（`streamMessage` 的 fetch + POST）**只挂调用方传入的 `signal`，没有任何 `setTimeout` / `AbortSignal.timeout`**。全仓唯一的请求超时在 `client.ts:338-348` 的 `probeProvider`（`timeoutMs = 15000`），聊天流式请求不走它。

因此可判定的失败条件：**只要上游迟迟不回首字节（长请求体 + 弱网 + 代理），`streaming[sessionId]` 会一直为真，`ReplyArea` 永久转圈，且没有任何一处会把它结束掉**；用户主动「停止」（`AbortController`）是唯一出口。这正是"短会话正常、长会话一直转"的形态。

#### 2.6 边界实测（同脚本输出）

| 场景 | 结果 |
|---|---|
| `rootMessageId` 链在某条消息处断裂（导入/异常数据缺 `selectedChildId`） | 可见消息 **2 / 总 6**，静默截断，不报错也不提示 |
| `selectedChildId` 成环（数据损坏） | 5 s 内返回，可见 6 条——`byId.delete(id)`（`branches.ts:31`）保证终止 |
| 末条回复 `status: 'streaming'`（上次进程被杀） | 上下文轮次 1，该条不计入上下文 |
| 全部消息无 `parentId`（旧线性数据） | `rootMessageId === undefined` → 直接返回全部 6 条（`branches.ts:19-21`） |

### 3. 结论

**真 bug（多因，且"数据读不出来"这一条归因是错的）**
- 打开长会话卡住 = **首帧全量渲染**（A3）+ 主线程被 Markdown/高亮同步占满；加载本身（IDB/反序列化/分支索引）实测亚毫秒级，不是原因。
- 发消息后一直转 = **请求上下文无裁剪**（A4）+ **全链路无超时**（A5）+ 历史附件串行补传，叠加后首字节永远等不到、状态永远收不尾。

### 4. 根因（`file:line`）

| 编号 | 根因 | 位置 |
|---|---|---|
| R1 | 消息列表全量渲染，无虚拟化、无分页、无「加载更早」 | `src/components/messages/MessageList.tsx:51`, `:149-174` |
| R2 | 请求上下文无 token/轮数裁剪，全量历史进 body | `src/services/chat/reply.ts:324-364`（`getContextRounds` `:287-297`）；`src/services/chat/store.ts:1108-1117` |
| R3 | 聊天请求无超时，只有 `probeProvider` 有 15 s | `src/services/api/client.ts:95-112`, `:269-288`；对照 `:338-348` |
| R4 | 历史附件串行补传，全部完成才发请求 | `src/services/chat/store.ts:900-920` |
| R5 | `ensureSessionLoaded` 两条静默 `return`（epoch 变更 / 摘要缺失）既不写缓存也不写错误 → 打开会话的转圈无出口 | `src/services/chat/store.ts:365-371` |

### 5. 修复建议

按"改动小、收益大、可独立验收"排序；建议本批只做 R2 + R3，R1 另开 issue。

**F1（必须，R3）请求超时 + 首字节超时**
- 在 `client.ts` 给 `request()` / `streamMessage` 加可选 `timeoutMs`，默认：连接与首字节 30 s，流内空闲 60 s（收到任一帧就重置计时器）。
- 超时映射为新的 `ApiErrorKind`（或在 `'stream'` 之外新增 `'timeout'`），文案走 i18n，`settleReply(reply,'error')` 后 `streaming` 必然被清 → 转圈一定结束。
- 影响面：`client.ts`（新增参数）、`store.ts:1068-1258`（传参 + catch 分支）、`errors.ts`（kind→文案）、i18n zh/en 各 1 条。不改协议、不改 DB schema。

**F2（必须，R2）上下文裁剪**
- 在调用 `toRequestMessages` 之前加纯函数 `fitHistory(history, budget)`：按字符数估算（中英分别加权）从最新往前保留，超预算的轮次丢弃并插入一条「前文已省略」提示；预算按 `spec.caps` 的上下文长度给默认值（如 60%），留回答预留。
- 纯函数、无副作用，可直接单测；不动 `toRequestMessages` 语义，只在 `store.ts` 调用处插入。
- 影响面：`reply.ts`（新增导出）+ `store.ts:1108`；`regenerateReply / continueReply / editMessage` 同路径受益。

**F3（建议，R5）加载失败必须可见**
- `store.ts:365-371` 两条 `return` 改为：epoch 变更 → 交给新 epoch 继续（不要静默丢弃）；摘要缺失 → 写 `sessionLoadErrors[id]`，让 `App.tsx:45-47` 的错误分支（已有重试按钮 `:127`）接管，而不是无限转圈。

**F4（另开 issue，R1）虚拟列表**
- `MessageList` 引入窗口化（首屏渲染最后 N 条 + 向上滚动增量加载），并把 `useReplyView` 的构建推迟到进入视口。这是长会话体验的根本解，但改动覆盖 `MessageList` / `ReplyArea` / 自动滚动 / `STICKY_THRESHOLD`，不宜与 F1/F2 同批。

**不做**：给 IDB 读加"分页"或改写 `loadSession`——实测证明那不是瓶颈，改了只增复杂度。

## #46 希望思考过程默认折叠，并且可以完全隐藏

### 1. 可验证断言

| # | 断言 | 判定 |
|---|---|---|
| B1 | 思考区**默认展开** | 成立（`useState(true)`） |
| B2 | 折叠状态是每条消息的组件本地状态，不持久化 | 成立 |
| B3 | 设置里**没有**「思考过程显示方式」这一项 | 成立（`settings.ts` 只有 `thinking: boolean` = 是否开启深度思考） |
| B4 | 没有「完全不显示」的能力 | 成立（`ReplyArea` 只在 steps 为空且非流式时整体不渲染） |

### 2. 证据

- `src/components/messages/ReplyArea.tsx:68`：`const [open, setOpen] = useState(true)` —— 每挂载一次就是展开；切会话/刷新即回到展开。
- `ReplyArea.tsx:86` 折叠箭头只调 `setOpen`；`:89-102` 步骤区由 `open || !title` 控制。
- `ReplyArea.tsx:71-73`：仅当 `view.steps.length === 0 && !(message.thinking && streaming)` 时整体 `return null` —— **这是唯一的「不显示」路径，与用户设置无关**。
- `src/services/settings.ts:11-33, 91-98, 122-125`：`Settings` 只有 7 个字段（`locale / themePreference / location / ttsVoice / thinking / search / siderCollapsed`），`thinking` 是「是否开启深度思考」（进请求体），**没有任何显示模式字段**；`KEYS`（`:26-33`）里也没有对应 localStorage key。
- i18n 现有 `thinking*` 一组键只覆盖「已深度思考（N 秒）」等文案，无「显示方式」文案。

> 按任务约定，本节**只出设计，不改代码**。

### 3. 结论

**设计如此 + enhancement**：当前「默认展开、不可全局配置、不可完全隐藏」是既定实现（不是 bug），issue 要的是新增能力。

### 4. 根因（`file:line`）

| 编号 | 现状 | 位置 |
|---|---|---|
| R6 | 默认展开写死在组件内 `useState(true)` | `src/components/messages/ReplyArea.tsx:68` |
| R7 | 折叠状态是 per-message 组件本地态，无持久化、无全局来源 | 同上（`open/setOpen` 作用域仅本组件） |
| R8 | 唯一「不渲染」条件由数据驱动，非用户可选 | `src/components/messages/ReplyArea.tsx:71-73` |
| R9 | 设置模型与持久化 KEYS 均无对应字段 | `src/services/settings.ts:11-33`, `:91-98` |

### 5. 修复建议（设计稿）

**状态模型**：新增三态 `ThinkingDisplay = 'collapsed' | 'expanded' | 'hidden'`
- `collapsed`（**默认**）：保留标题行（「已深度思考（N 秒）」+ 箭头），内容收起，可点开。与今天"点开一次"的交互一致。
- `expanded`：保留今天的行为（进入即展开）。
- `hidden`：**整块不渲染、不占空间**——标题行、箭头、思考 markdown、耗时全部不出现。`ReplyArea` 的提前返回条件改成 `view.steps.length === 0 || display === 'hidden'`，且不影响正文渲染。

**落地改动（5 处，均为小改）**
1. `src/services/settings.ts`：`Settings` 加 `thinkingDisplay: ThinkingDisplay`；`KEYS.thinkingDisplay = 'chat-demo:thinking-display'`；读取时白名单校验（非法值回落 `'collapsed'`）；导出 `setThinkingDisplay`。**不进请求体**（与 `thinking` 开关正交）。
2. `src/components/messages/ReplyArea.tsx`：`useState(true)` → 初值取自 `useSettings((s) => s.thinkingDisplay)`；本地 `open` 初值 = `display === 'expanded'`；`hidden` 时提前返回。
3. **零占位**：`hidden` 走「不渲染 DOM」而不是 `display:none`——外层 flex/grid 的 gap 仍会占位，必须整块不产出节点。
4. i18n：`src/i18n/zh.ts` / `en.ts` 各加 4 条，键名成对——`thinkingDisplayTitle` / `thinkingDisplayCollapsed` / `thinkingDisplayExpanded` / `thinkingDisplayHidden`。两文件键集合必须完全一致（跑现有 parity 用例）。
5. 设置面板：在「深度思考」开关下方加三选一（`role="radiogroup"` + `aria-pressed`，复用现有分段控件样式），落在 `src/components/settings/` 对应分节。

**流式中途折叠**：`ReplyArea.tsx:86` 的箭头在流式期间已可点（不受 `streaming` 限制）。只需保证用户手动点击**覆盖**全局默认值且不被每帧重置：
```ts
const display = useSettings((s) => s.thinkingDisplay)
const [override, setOverride] = useState<boolean | null>(null)   // null = 跟随设置
const open = override ?? display === 'expanded'
```
`override` 属于该消息实例，符合「每条消息独立折叠」的直觉；`hidden` 下即使流式也不渲染，避免 thinking 的 loading 抖动被带出来。**注意**：新分支必须放在所有 hooks 之后（`useTicker` 在 `:39-49`、现有 `return null` 在 `:71-73`），否则 hooks 顺序会随状态变化而错乱。

**持久化**：写 localStorage（与 `settings.ts` 其余字段一致），刷新后保持；跨设备不同步（与现有设置一致）。

**默认值取舍**：issue 明确要「默认折叠」，故 `collapsed` 为默认；未设置过的老用户行为会从「展开」变「折叠」——这是 issue 要求的预期变化，需在 release note 点明。

**影响面**
- 改动文件：`settings.ts`、`ReplyArea.tsx`（+ 可能 `ReplyArea.module.css`）、`zh.ts`、`en.ts`、设置面板一个分节。
- 不改：请求体、DB schema、`store.ts`、导出格式。
- 风险点：`hidden` 时 `AssistantMessage.tsx` 里 `waiting` 的计算（在 `ReplyArea` 之上）不受影响；但「思考中的 loading 指示」一旦全不渲染，用户在长思考期间可能看起来像没反应——建议 `hidden` 下在辅助文本区保留一句极简状态（可选，需产品确认）。

## #44 安卓未接管 onRenderProcessGone，渲染进程被回收后整个应用被杀

### 1. 可验证断言

| # | 断言 | 判定 |
|---|---|---|
| D1 | `android/` 源码里没有任何 `onRenderProcessGone` 实现 | 成立（grep 命中 0） |
| D2 | `MainActivity` 是裸 `BridgeActivity`，只注册了 4 个插件 | 成立 |
| D3 | Capacitor 8.6.2 **已提供**接管入口，但默认返回 `false`（= 未处理） | 成立 |
| D4 | 因此 Chromium `aw_browser_terminator` 判定「无 webview 接管」，走「杀应用」分支 | 与日志一致 |

**Capacitor 侧（`node_modules/@capacitor/android` v8.6.2）留了钩子，但默认不处理**

- `BridgeWebViewClient.java:92-104`：
  ```java
  public boolean onRenderProcessGone(WebView view, RenderProcessGoneDetail detail) {
      super.onRenderProcessGone(view, detail);
      boolean result = false;
      for (WebViewListener listener : bridge.getWebViewListeners()) {

  ```
- `WebViewListener.java:53-56`：`public boolean onRenderProcessGone(...) { return false; }`，注释写明 “Return true if the state is handled”。
- `Bridge.java:1499-1501`：`public void addWebViewListener(WebViewListener l)` 是唯一注册入口；`Bridge.java:209,281` 把 `BridgeWebViewClient` 挂到 WebView 上。

链路还原：WebView 渲染进程被杀（OOM）→ `BridgeWebViewClient.onRenderProcessGone` 被调 → `bridge.getWebViewListeners()` 为空 → 返回 `false` → 未接管 → Chromium `aw_browser_terminator.cc(112)` 打日志并**杀应用**，与 issue 的 logcat 完全一致：

```

           wasn't handed by all associated webviews, killing application.
```

**另需区分**：#27（`src/services/chat/sessionGroups.ts:25` 的 `.at(-1)` 缺 ES2022 polyfill，旧 WebView 抛 TypeError）是**独立缺陷**，它可能让页面崩溃但不产生 `aw_browser_terminator` 日志；两者不能合并成一条修复。

### 3. 结论

**真 bug（静态确认）**：应用侧完全没有接管渲染进程回收事件，`return false` 直接导致整个应用被系统杀掉。修复方向明确、代码量小。

> **未在设备上验证**：本节全部为静态代码分析 + 依赖库源码比对，未在 Android 真机/模拟器上复现 OOM kill，也未跑修改后的 APK。

| R17 | `BridgeWebViewClient` 把所有 listener 返回值 OR 起来，全 false 则 false | `.../BridgeWebViewClient.java:92-104` |

### 5. 修复建议

只允许**一套**实现（issue 已约定），推荐**方案 A：在现有 PR #29 基础上补齐**，标题改为 `Refs #27, fixes #44`。

**代码形态（`MainActivity.onCreate`，`super.onCreate` 之后）**

```java
getBridge().addWebViewListener(new WebViewListener() {
    @Override
    public boolean onRenderProcessGone(WebView view, RenderProcessGoneDetail detail) {
        if (handling) return true;   // 1) 防重入：一次 OOM 可能回调多次
        handling = true;
        try {
            Log.e("DeepSeekChat", "renderer gone, didCrash=" + detail.didCrash());  // 3) 记录原因
            ViewGroup parent = (ViewGroup) view.getParent();
            if (parent != null) parent.removeView(view);
            view.destroy();
            // 4) 重建必须 post 到 UI 队列末尾，不能在回调栈里直接 recreate()
            view.post(() -> {
                try { recreate(); } catch (Throwable t) { Log.e("DeepSeekChat", "recreate failed", t); }
            });
        } catch (Throwable t) {       // 2) 异常不能逃逸，逃逸等于没接管
            Log.e("DeepSeekChat", "onRenderProcessGone handling failed", t);
        }
        return true;                  // ← 关键：声明已接管，否则系统杀应用
    }
});
```

必须闭合的 4 个坑（PR #29 的缺口）：
1. **重入保护 + try/catch**：`handling` 布尔 + 全包 try；异常逃逸等价于 `return false`。
2. **`getBridge()` 判空**：`super.onCreate` 之前取会拿到 null，故只在之后调用并判空。
3. **记录 `detail.didCrash()`**：区分 OOM 与 update 两种回收原因，写进 logcat，不进用户可见文案。
4. **`recreate()` 放进 `view.post(...)`**：在渲染进程死亡回调栈里直接 `recreate()` 会与 WebView 内部状态冲突，典型表现是二次崩溃或白屏。

配套（同批、低成本）：
- `AndroidManifest.xml` 给 `application` 加 `android:largeHeap="true"`（OOM 是诱因之一，成本极低；**不是**根因修复）。
- 通过既有 `DiagnosticsDevicePlugin` 把 `didCrash` 与时刻记一条，作为 beta.10 的观测数据。
- **不要**在 JS 侧加「崩溃后重载 URL」的逻辑：应用被杀时 JS 上下文已消失，那条路径无效。

**影响面**
- 只改 `MainActivity.java`（+1 方法、+1 import、+1 字段），必要时 1 行 manifest。
- 不改 Web 侧代码、不改 Capacitor 依赖、不改构建脚本。
- 风险：`recreate()` 会重建整个 Activity，若崩溃发生在对话进行中，内存态会丢——但这本来就是现状（整个进程被杀），所以严格优于现状。
